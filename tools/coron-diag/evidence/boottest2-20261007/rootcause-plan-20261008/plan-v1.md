# 次の調査と修正の方針（案。2026-10-08、実機は触っていない）

## 目的と完了条件
目的: 本番で使うファームのキーマップを通常の手順（GitHub Actions のビルド → UF2 を書き込み）で更新したとき、手動リセットなしで起動し、キー入力を含む必要な機能が動くこと。
本番像への復帰や、試験像で事故記録 0 件だったことは、修復完了とみなさない。

## 根拠にした事実（取得済みのログから）
1. 停止 4 件は Windows の PnP ログ（Kernel-PnP/Device Management、取り外しの行だけが残る。現れた側の行は Configuration ログに該当が無く、読めない）で 2 つの型に分かれる。Coron 右手側の USB ポートは `Port_#0006.Hub_#0001`（受動的に読み取り）。
   - 型 S1（書き込み直後の 3 件: 10/04 20:35、10/05 09:26、10/05 19:42）: ブートローダーのドライブが消えた（= 像を受けて直接ジャンプした）あと、2 分半、約 20 分、22 分のあいだ、Port 6 には本体（VID_1D50）も列挙失敗（VID_0000）も無い。つまり起動は USB のプルアップを出す段階（Zephyr の USB 有効化）まで進んでいない。
   - 型 S2（10/07 16:16 の 1 件）: 16:09:54 に本体が消えた（再起動）あと、16:10:00、16:13:53、16:15:44 の 3 回、Port 6 に「接続はしたが記述子に応答しない」失敗（VID_0000&PID_0002、id=1011）が記録され、16:25:24 のリセット押下まで本体は現れない。つまりこの型は USB の有効化まで進み、そのあと列挙に応答できない状態で止まっている。これまでの「USB 初期化（優先度 96）より前で止まった」という絞り込みは S2 には当たらない。同じ 6 分間に失敗が 3 回続いたことは、致命的エラー（`lll_central.c:252` の検査）→ 再起動 → 止まる、が繰り返された形と整合する（記録は最後の 1 件だけ）。
2. 「ピンリセットだけは止まらない」は確立していない。ブートローダーの経路はピンリセットとソフトリセットで同じ（issue の調べ）で、ピンリセットは停止の回復時にしか押されておらず（4 回）、4/33 の率なら 4 回で 0 の確率は約 0.7。
3. 試験像での 0/179 と現場の 4/33 の差も確立していない。4/33 の 95% 区間はおよそ 3〜28% で、下限なら 179 回で 0 の確率は数%ある。「試験像では起きない条件がある」とは言い切れない。
4. 本番像と試験像の差分は、試験像の `.conf` に書かれた 3 行（`CONFIG_CORON_DIAG_BOOT=y`、`CONFIG_ZMK_WATCHDOG_FREEZE_DETECT=n`、最適化像は `CONFIG_SPEED_OPTIMIZATIONS=y`）と、計測器モジュール自身（早期フック、各段の `SYS_INIT` の刻印、TIMER4 の網、コンソール命令）。早期フックは `.bss` 初期化の後、Zephyr のクロック初期化（PRE_KERNEL_1）の前に走り、記録領域の CRC 検査と入口レジスタの写しに数十 µs 使う。入口の写しは「受け渡しの瞬間」ではなく `.bss` 初期化後の状態（計測器のコメントにも明記）。
5. 試験像の 179 回の起動で、入口の状態は毎回同じ（LFCLK 停止、ブートローダーが残した `LFCLKSTARTED`/`HFCLKSTARTED` のイベント、HFINT 動作中、RESETREAS=SREQ）。受け渡しの瞬間（RAM 初期化より前、ジャンプ直後）の状態は測っていない。
6. ブートローダー 0.6.1（commit 97fbda5。調査役が本家の生ソースから引用、`bootloader-exit-0.6.1.md`。Seeed 配布版の差分は未確認）の DFU 完了後の出口: `NVIC_SystemReset()` を通らず同じ `main()` から `usb_teardown()` → `board_teardown()` → `bootloader_app_start()` で直接ジャンプ。残るもの（引用）: USBD は ENABLE=0、プルアップ 0、割り込み 0。LFCLK と HFCLK は STOP タスクを出すだけで完了を待たない。RTC1 は STOP と CLEAR、SysTick は CTRL=0。NVIC は ICER/ICPR を全ビット書く。全ピンは既定へ、PWM は無効。残るもの（ソースに処理が見つからないことからの推測）: `EVENTS_LFCLKSTARTED`/`HFCLKSTARTED` の消去なし（計測器の入口観測と一致）、`LFCLKSRC` は RC のまま、POWER の USB イベント割り込み許可（`nrfx_power_usbevt_enable` の対になる無効化が無い）、NVIC の優先度（USBD、SysTick、RTC1、SWI）、SysTick の保留ビット、RTC1 の PRESCALER と CC。通常の起動（DFU に入らないジャンプ）との差は「USB を一度も有効にしない」ことだけで、`board_teardown` と `bootloader_app_start` は共通。
   この表から、書き込み直後の経路だけに残りうるのは「POWER の USB イベント割り込み許可」と「HFXO 停止の完了待ちなし」の 2 点。POWER と CLOCK は同じ割り込み線（POWER_CLOCK）を使うので、Zephyr のクロックドライバがこの線を有効にした瞬間に、ブートローダーが残した許可とイベントの組み合わせで割り込みが入りうる。これが起動を止めるかはソースだけでは決められず、T1 で許可とイベントの実値を測る。

## 候補と判別
| 候補 | 整合する型 | 予測 | 判別の試験 | 結果が修正につながる形 |
|---|---|---|---|---|
| A. ブートローダーからの受け渡し状態（クロック、RTC1、NVIC、USBD、保留割り込み）に、Zephyr の初期化が想定しないものが残る。DFU 直後のジャンプ（`usb_teardown` → `board_teardown` → ジャンプ、リセットなし）で顕著 | S1 | 受け渡しの瞬間のレジスタに、経路（DFU 直後 / ソフトリセット）で差があり、時々「汚れた」値（LFCLK 動作中、RTC1 動作中、NVIC 有効、USBD 有効、保留割り込み）が出る | T1: リセットハンドラの先頭（`soc_reset_hook`、RAM 初期化より前）でレジスタを記録領域へ写す試験像で、DFU 直後 20 回と `r` 20 回の入口状態の分布を取る。「停止が起きるのを待つ」のではなく、疑っている変数を毎回測る | 汚れが観測されれば、同じフックで仕様どおりに整える処理（LFCLK 停止を待つ、HFXO 停止を待つ、RTC1 停止、NVIC 全無効と保留消去、USBD 無効）を入れ、同じ測定で「Zephyr が見る状態が経路によらず同一」を確かめる（再現に頼らない検証条件）。観測されなければ A は退け、B と C へ |
| B. USB の有効化の直後に、カーネルの進行が止まる（システムタイマ、USB ワークキュー、割り込み）。致命的エラー後の再起動で起きやすい | S2 | 再起動の直後、USB の接続はできるが列挙に応答しない | T3: 試験像で割り込み文脈から人工の致命的エラーを起こし（コンソール命令で TIMER の ISR 内で `k_oops()`）、再起動が完了して USB が再列挙するかを見る（1 回 1 分、10 回）。あわせて watchdog モジュールの致命的エラー処理が、フォルト文脈で待つ呼び出し（設定保存、ミューテックス）をしていないかをソースで確かめる | 再列挙に失敗すれば、致命的エラー処理（記録の保存を次の起動へ繰り延べ、即 `sys_reboot`）を直す。成功すれば B の「致命的エラー経由」は退け、S2 は 10/07 の構成（`LL_ASSERT_OVERHEAD` の検査が有効だった版）固有の可能性が残る |
| C. 偶然（試験像の率は現場と変わらない） | S1、S2 | 試験像でもいずれ起きる | 判別の試験は無い（回数を増やす形になるので採らない） | 発生時に場所が分かる仕組み（本番像の RAM に段階の印を 1 語だけ残し、次の起動で読む）が要る。計測処理を本番に残さない決定と衝突するので、リーダーの判断事項として挙げるだけ |

候補 A を最初に置く理由: 書き込み直後の 3 件が型 S1 で、通常の手順（UF2 書き込み）そのものの経路だから。候補 A は「汚れた状態が一度でも観測されるか」で白黒がつき、修正の検証も同じ測定で済む。

## 手順
T0 机上（約 1.5 時間、実機なし）
- ブートローダー 0.6.1 の DFU 完了後の出口（`usb_teardown`、`board_teardown`、ジャンプ）が何を有効のまま残すかをソースから表にする（NVIC、保留割り込み、USBD、USB レギュレータ、HFXO、LFCLK、RTC1、PPI、GPIOTE、VTOR、SysTick）。調査役（researcher）に切り出す。
- Zephyr 4.1 の nRF52 の起動（リセットハンドラ → `soc_reset_hook` → RAM 初期化 → PRE_KERNEL_1 のクロックとタイマ → … → USB 有効化）が各段で何を前提にするかを突き合わせ、T1 で測る項目を確定する。
- watchdog モジュールの致命的エラー処理を読み、フォルト文脈で待ちうる呼び出しの有無を確かめる（T3 の前提）。
T1 実機（試験像だけ。ビルド 15 分、実行 25 分、復帰 1 分）
- 計測器に `soc_reset_hook` の写しを足し（RAM 初期化前なので記録領域だけに書く。読み取りと書き込みだけで待ちは無い）、dump に `entry0` 行として出す。測る項目（事実 6 の表から）: CLOCK の `LFCLKSTAT`、`LFCLKRUN`、`LFCLKSRC`、`HFCLKSTAT`、`HFCLKRUN`、`INTENSET`、`EVENTS_LFCLKSTARTED`、`EVENTS_HFCLKSTARTED`。POWER の `INTENSET`、`EVENTS_USBDETECTED`、`EVENTS_USBPWRRDY`、`EVENTS_USBREMOVED`、`USBREGSTATUS`、`RESETREAS`。USBD の `ENABLE`、`USBPULLUP`、`INTEN`。RTC1 の `COUNTER`（2 回読んで動いているか）、`INTENSET`、`EVTEN`、`PRESCALER`。NVIC の `ISER[0..1]`、`ISPR[0..1]`、`IPR` のうち USBD、POWER_CLOCK、RTC1、SWI の 4 本。SCB の `VTOR`、`ICSR`（保留の SysTick と PendSV）、`SHCSR`。SysTick の `CTRL`。PRIMASK。
- 既存のループで、DFU 直後の起動 20 回（bt4 と bt4A の交互書き、稼働 1 分）と `r` 20 回を回し、各起動の `entry0` を集める。停止条件、子の終了確認、本番復帰は既存のまま。
- 判定: 経路ごとの分布を表にし、「汚れ」が 1 回でもあれば候補 A を採って T2 へ。全回で清浄なら候補 A を退け、T3 と、候補 C の判断事項をリーダーに出す。
T2 修正（候補 A が採れたときだけ。ビルド 20 分、測定 25 分、本番の更新 30 分）
- 設定リポジトリに `CONFIG_SOC_RESET_HOOK=y` と、受け渡し状態を仕様どおりに整える `soc_reset_hook()` を入れる（fork も `--wrap` も使わない。Nordic 版 MCUboot がジャンプ前に行う整え方と同じ考え）。試験像で T1 の測定を繰り返し、Zephyr が見る状態が経路によらず同一であることを確かめる。
- 本番像をこの変更入りでビルドし、通常の手順（UF2 を `b` で書き込み）で更新して、手動リセットなしに USB の HID と CDC が列挙され、PC と BLE の HID がつながり、Studio の RPC が応答することを確かめる。
T3 実機（候補 B。ビルド 10 分、実行 10 分）
- 試験像に ISR 文脈の人工致命的エラーの命令を足し、再起動が完了して USB が再列挙するかを 10 回見る。

## 所要時間の見込み
机上 1.5 時間、実機 T1 約 40 分、T2 約 1.5 時間（採ったとき）、T3 約 20 分。合計 3〜4 時間で、待ちは実機の書き込みと起動の観測だけ（試行回数を増やす要素は無い）。

## 失敗時の復旧
- 実機の操作はすべて既存のループと書き込みスクリプト（期限つき子プロセス、終了確認、`calib-flash.ps1 -Expect prod` による本番復帰）で行う。試験像は TIMER4 の網（起動 20 秒、稼働 15 秒）で止まりを自動で再起動する。
- 残る穴: `soc_reset_hook` より前（ブートローダーのジャンプ直後の数命令）で止まった場合は網が張られておらず、リセット押下でしか戻らない。フックは読み書きだけで待ちを持たないので、ここで止まる機構は見えていないが、ゼロとは言えない。
- 本番の更新（T2）で起動しなければ、既存の復帰（同じ像の書き直し、それでも出なければ従来どおりリセット 1 回）に戻る。

## 確認できた条件と残る不確実性（この方針を終えたときに言えること）
- 言えること: 受け渡しの瞬間の状態の分布（経路ごと）。候補 A の採否。採った場合は「Zephyr が見る受け渡し状態が経路によらず同一」という、再現に頼らない検証結果。候補 B の採否（人工の致命的エラーからの復帰の成否）。
- 言えないこと: 停止の率は 3〜28% の幅があるので、修正後の更新 N 回で 0 件でも「直った」とは言えない。修正が効いたと言えるのは「観測した汚れが消えた」範囲まで。候補 A も B も退けられた場合、残るのは候補 C で、発生時に場所を残す仕組みの採否はリーダーの判断になる。
- 型 S1 の 3 件のうち、BLE 側も死んでいたと明記があるのは 10/05 09:26 の 1 件だけ（ほかは USB だけが確認されている）。「USB だけが出ない（本体は動いている）」の可能性は 10/04 と 10/05 19:42 では消えていない。
- キー入力の最終確認は、人の押下が要る（スクリプトから鍵を打てない）。途中の立ち会いは不要だが、完了条件の最後の 1 回だけはリーダーに押してもらう形になる。
