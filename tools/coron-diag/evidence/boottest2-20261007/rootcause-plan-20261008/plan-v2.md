# 次の調査と修正の方針 v2（2026-10-08。v1 への Codex レビュー「作り直し」の 8 点を反映。実機は触っていない）

## 目的と完了条件
目的: 本番で使うファームのキーマップを通常の手順（GitHub Actions のビルド → UF2 の書き込み）で更新したとき、手動リセットなしで起動し、必要な機能が動くこと。
本番像への復帰や、試験像で事故記録 0 件だったことは、修復完了とみなさない。
完了条件のうち「キー入力」は、スクリプトから物理キーを押せないので、次のどちらかをリーダーに決めてもらう: (a) 自動で確かめられる代替（USB の HID インターフェースの列挙、PC との BLE HID 接続、Studio の RPC がキーマップに応答）で置き換える、(b) 立ち会いではなく「リーダーが都合のよいときに 1 度キーを押して報告する」を完了条件の最後に置く。

## 取得済みの記録から言えること（言い過ぎを直した）
1. Windows の PnP ログ（Kernel-PnP/Device Management）に残るのは取り外しの行だけで、現れた側の行は読めない。Coron の USB ポートは `Port_#0006.Hub_#0001`。
   - 書き込み直後の 3 件（10/04 20:35、10/05 09:26、10/05 19:42）: UF2 ドライブの取り外し記録のあと、次に本体（VID_1D50）の取り外しが記録されるまでの 2 分半、約 20 分、22 分のあいだ、Port 6 には対象 VID/PID の取り外し記録も列挙失敗ノード（VID_0000&PID_0002）の取り外し記録も無い。「USB の有効化まで進まなかった」は推測で、言えるのは「取り外し記録が無い」まで。
   - 10/07 16:16 の 1 件: 16:09:54 の本体の取り外し記録のあと、同じ物理ポートに列挙失敗ノードの取り外し記録が 16:10:00、16:13:53、16:15:44 の 3 回ある。VID_0000&PID_0002 は Windows が列挙に失敗したデバイスに付ける代名で、原因は記述子の無応答に限らず、1 つの接続にホストが複数回再試行するので「3 回再起動した」とは言えない。言えるのは「この型では USB に何かが現れた」まで。書き込み直後の 3 件と型が違う可能性はあるが、断定しない。
2. ブートローダー 0.6.1（本家 97fbda5。Seeed 配布版との差分と、実機のブートローダーとのバイト同一性は未確認）の DFU 完了後の出口（調査役が生ソースから引用、`bootloader-exit-0.6.1.md`）: `NVIC_SystemReset()` を通らず同じ `main()` から直接ジャンプ。USBD は無効、NVIC は全無効と保留消去、RTC1 は停止と消去、SysTick は CTRL=0、全ピン既定。LFCLK と HFCLK は STOP を出すだけで完了を待たない。ソースに処理が見つからないもの（推測）: `EVENTS_*STARTED` の消去、POWER の USB イベント割り込み許可の解除、NVIC 優先度の復元、SysTick の保留ビット。通常の起動（DFU に入らないジャンプ）との差は「USB を一度も有効にしない」ことだけ。
3. 試験像の 179 回（10/07 の 172 回 + 今日の 7 回）の入口記録は毎回同じ: LFCLK 停止、`LFCLKSTARTED` と `HFCLKSTARTED` のイベントが残っている、HFINT 動作中、RESETREAS=SREQ。記録は `board_early_init_hook`（`SystemInit` と RAM 初期化の後）で取っていて、NVIC、SysTick、VTOR、USBD、POWER と CLOCK の割り込み許可、RTC1 の許可は入っていない。
4. 統計（Clopper-Pearson）: 現場の 4/33 の 95% 区間は約 3.4〜27%。率を 4/33 と置くと回復時のピンリセット 4 回で 0 件になる確率は約 60% なので、「ピンリセットは止まらない」は確立していない。率を下限の 3.4% と置いても試験像の 179 回で 0 件になる確率は約 0.4% で、試験条件では率が大幅に低いことが示唆される。ただし像（計測器入り、freeze 検出なし）、稼働時間、入り方が現場と違い、同一個体の反復なので、独立な二項試行として原因は推定できない。
5. 本番像と試験像の差分: `.conf` の 3 行（`CONFIG_CORON_DIAG_BOOT=y`、`CONFIG_ZMK_WATCHDOG_FREEZE_DETECT=n`、最適化像は `CONFIG_SPEED_OPTIMIZATIONS=y`）と計測器モジュール自身（早期フック、段階の刻印、TIMER4 の網、コンソール命令）。
6. watchdog モジュールの致命的エラー処理は、RAM の保留記録を作って即再起動し、設定の保存は次の起動へ繰り延べている（`watchdog_fatal.c`、`watchdog_pending.c`。Codex が確認）。「保存で固まる」は候補から外れる。Zephyr 共通の fatal 経路はその前にログと coredump を通る（本番の `.config` でログの出力先が有効かは未確認。T3 の机上で確かめる）。
7. 既存の修正候補（`CONFIG_CORON_DIAG_BOOT_FIX` の `lf_clean_stop`）には誤りがある: HFXO の停止待ちが `HFCLKSTAT.STATE==0` だが、HFXO を止めても HFINT に戻るだけで STATE は動作中のまま。待つべきは `HFCLKSTAT.SRC` が RC に戻ること。この候補はこのままでは使わない。

## 無人復旧の穴（先に決めること）
- 本番復帰のスクリプトは、実機が app か boot として USB に見えるときしか進めない。試験像の TIMER4 の網は `board_early_init_hook` で張られるので、それより前（ブートローダーのジャンプ直後〜フック）で止まると、自動では戻らずリセット押下が要る。これは今日までのループにもあった穴で、今回の案も同じ。
- 選択肢: (i) この穴を承知のうえで、網より前に新しい処理を足さない形（T1 は既存のフックの中で読むだけ）に限って進める。(ii) ホストから電源を切れる設備（ポートごとに給電を切れる USB ハブ。`uhubctl` 対応のもの。購入が要る）を入れてから、網より前に手を入れる試験（T2 の整え処理）へ進む。(iii) 無人の制約のもとでは網より前の試験は行わない。
- v2 の T1 と T3 は (i) で進められる。T2（整え処理）と、新しい像の初回起動で一度ソフトリセットする比較像は、網より前に処理を足すので (ii) か、リーダーが (i) の穴を明示的に受け入れたときだけ。

## 手順と所要時間（Codex の指摘で見積もりを直した）
T0 机上（約 2 時間、実機なし）
- Zephyr 4.1 と nrfx の初期化コード（クロックドライバ、POWER_CLOCK の共有 ISR、USB ドライバの POWER イベント登録、RTC1 のシステムタイマ、NVIC の接続）が前提にする入口状態を表にし、T1 の禁止条件を定義する。
- 本番の `.config` で Zephyr のログの出力先と coredump を確かめる（T3 の机上）。
- `SystemInit`（nrfx の `system_nrf52.c`）が触るレジスタを表にし、T1 で足す項目がその後でも意味を持つことを確かめる。
T1 実機（試験像だけ。実装と模擬 1.5 時間、ビルド 20 分、実行約 75 分、復帰 1 分）
- 計測器の入口記録に上の項目を足し、dump の行（`entry3`〜）、ホストの検証表、模擬の缶詰を更新する。既存の校正と模擬 83 場面で回帰を確かめる。
- ループで、DFU 直後の起動 20 回（bt4 と bt4A の交互書き、稼働 1 分。1 回あたり書き込み約 50 秒 + 稼働 1 分 + 観測 30 秒 ≒ 2.3 分で約 46 分）と `r` の起動 20 回（1 回約 1 分で約 20 分）を回す。停止条件、子の終了確認、本番復帰は既存のまま。
- 判定は禁止条件の表に照らし、経路ごとの分布を記述統計として残す。
T3 実機（候補 B。実装 30 分、ビルド 20 分、実行 10 分）
- 人工の致命的エラー 1 回。前後の PnP と入口記録、保留記録を保存する。
T2 修正（T1 で禁止条件に当たったときだけ。仕様表 1 時間、実装と模擬 2 時間、測定 75 分、本番の更新 30 分。無人復旧の (ii) か明示の受け入れが前提）
- 整え処理か初回リセットの比較像を作り、T1 と同じ測定で「Zephyr が見る状態が経路によらず同一で、禁止条件に当たらない」ことを確かめる。
- 本番像に入れて通常の手順で更新し、手動リセットなしに USB の HID と CDC が列挙され、BLE HID がつながり、Studio の RPC が応答することを確かめる。
合計: 机上 2 時間、T1 約 3.5 時間、T3 約 1 時間、T2 約 5 時間（採ったとき）。待ちは書き込みと起動の観測だけで、試行回数を増やす要素は無い。

## 失敗時の復旧
- 実機の操作は既存のループと書き込みスクリプトで行い、本番復帰は `calib-flash.ps1 -Expect prod`（初期状態が app か boot のときだけ進める）。試験像は TIMER4 の網で、フック以降の停止を自動で再起動する。
- T1 は網より前に処理を足さない（フックの中で読むだけ）ので、今日までのループと同じ穴しか無い。T2 は網より前に処理を足すので、上の「無人復旧の穴」の判断が先。
- 本番の更新で起動しなければ、同じ像の書き直しまでは自動で行い、それでも出ない場合は「無人の制約では戻せない」と報告して止まる。

## この方針を終えたときに言えること、言えないこと
- 言えること: DFU 直後と `r` の入口状態の経路差（項目ごと）。禁止条件に当たる項目の有無。候補 B の機構試験 1 回の結果。T2 まで進めば「Zephyr が見る入口状態が経路によらず同一」という、再現に頼らない検証結果。
- 言えないこと: 現場の率は 3.4〜27% の幅があり、修正後の更新 N 回で 0 件でも「直った」とは言えない。修正が効いたと言えるのは、観測した禁止条件が消えた範囲まで。
- 書き込み直後の 3 件で BLE 側も止まっていたと明記があるのは 10/05 09:26 の 1 件だけ。残り 2 件は USB の観測だけで、「本体は動いていて USB だけ出ない」は消えていない。
- 実機のブートローダーが本家 0.6.1 と同じ出口を持つかは、Seeed 配布版の差分とバイト同一性を確かめるまで推測。

## リーダーの判断が要る点
1. 無人復旧の穴の扱い: (i) 受け入れて T1 と T3 だけ進める、(ii) ポートごとに給電を切れる USB ハブを入れてから T2 へ、(iii) 網より前の試験はしない。
2. 完了条件の「キー入力」: 自動の代替 (a) か、最後の 1 度の押下 (b) か。
3. 候補 C の「発生時に場所を残す 1 語の印」を本番に入れるか。
