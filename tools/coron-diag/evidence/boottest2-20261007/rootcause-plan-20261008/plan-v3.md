# 次の調査と修正の方針 v3（2026-10-08。Codex の 2 回のレビュー（v1「作り直し」、v2「条件つきで採用」）を反映した最終案。実機は触っていない）

## 目的と完了条件
目的: 本番で使うファームのキーマップを通常の手順（GitHub Actions のビルド → UF2 の書き込み）で更新したとき、手動リセットなしで起動し、必要な機能が動くこと。本番像への復帰や、試験像で事故記録 0 件だったことは、修復完了とみなさない。
完了条件は自動で確かめられるものに限る: 更新後に手動リセットなしで、USB の HID と CDC が列挙され、PC との BLE HID 接続が確立し、Studio の RPC がキーマップの問い合わせに応答すること。物理スイッチとキーマトリクスの動作は、この方針では未確認のまま残る（人の押下を求めない制約のため。キー押下を完了条件に置く案はレビューで制約違反と判定され、外した）。

## 取得済みの記録から言えること（断定を避けた表現）
1. Windows の PnP ログ（Kernel-PnP/Device Management）に残るのは取り外しの行だけで、現れた側の行は読めない。Coron の USB ポートは `Port_#0006.Hub_#0001`。
   - 書き込み直後の 3 件（10/04 20:35、10/05 09:26、10/05 19:42）: UF2 ドライブの取り外し記録のあと、次に本体（VID_1D50）の取り外しが記録されるまでの 2 分半、約 20 分、22 分のあいだ、Port 6 には対象 VID/PID の取り外し記録も列挙失敗ノードの取り外し記録も無い。言えるのは「取り外し記録が無い」まで。
   - 10/07 16:16 の 1 件: 16:09:54 の本体の取り外し記録のあと、Windows が同じ物理ポートに列挙失敗ノード（VID_0000&PID_0002。Windows が正しい VID/PID を取れなかったときに作る代名で、原因はポートリセット、アドレス設定、記述子の取得や検証のどの段階でもありうる）を作り、その取り外しが 16:10:00、16:13:53、16:15:44 の 3 回記録された。原因の段階と、物理的な再接続の回数は不明。書き込み直後の 3 件と型が違う可能性はあるが断定しない。
2. ブートローダー 0.6.1（本家 97fbda5。Seeed 配布版との差分と、実機のブートローダーとのバイト同一性は未確認）の DFU 完了後の出口（調査役が生ソースから引用、`bootloader-exit-0.6.1.md`）: `NVIC_SystemReset()` を通らず同じ `main()` から直接ジャンプ。USBD は無効、NVIC は全無効と保留消去、RTC1 は停止と消去、SysTick は CTRL=0、全ピン既定。LFCLK と HFCLK は STOP を出すだけで完了を待たない。ソースに処理が見つからないもの（推測）: `EVENTS_*STARTED` の消去、POWER の USB イベント割り込み許可の解除、SysTick の保留ビット。確認したソース上の制御フローの差は「DFU の経路だけが USB を初期化して終了する」ことで、その実行が CLOCK、POWER、PPI などに残す結果の差が候補 A の主題。
3. 試験像の 179 回の入口記録（`board_early_init_hook`。`SystemInit`、Zephyr の割り込み全無効と保留消去、VTOR と優先度の設定、RAM 初期化の後）は毎回同じ: LFCLK 停止、`LFCLKSTARTED` と `HFCLKSTARTED` のイベントが残る、HFINT 動作中、RESETREAS=SREQ。
4. 統計（Clopper-Pearson、両側 95%）: 現場の 4/33 の区間は約 3.40〜28.20%。率を 4/33 と置くと回復時のピンリセット 4 回で 0 件になる確率は約 60% で、「ピンリセットは止まらない」は確立していない。率を下限の 3.40% と置いても試験像の 179 回で 0 件になる確率は約 0.20%（0/179 の 95% 上限は片側約 1.66%）。試験条件間に大きな率の差があることは示唆されるが、像（計測器入り、freeze 検出なし）、稼働時間、入り方が現場と違い、同一個体の反復なので、独立な二項試行として原因は推定できない。
5. 本番像と試験像の差分: `.conf` の 3 行（`CONFIG_CORON_DIAG_BOOT=y`、`CONFIG_ZMK_WATCHDOG_FREEZE_DETECT=n`、最適化像は `CONFIG_SPEED_OPTIMIZATIONS=y`）と計測器モジュール自身。
6. 致命的エラーの経路（机上で確認済み）: watchdog モジュールは RAM の保留記録を作って即再起動し、設定の保存は次の起動へ繰り延べる。Zephyr 共通の経路はその前にログと coredump を通るが、この構成は `CONFIG_LOG` も coredump も無効で、フォルトの内容は何も出力しない。CDC ACM の `poll_out` は割り込み文脈ではリングが満杯でも捨てて戻る。「出力で固まる」機構は無い。
7. 既存の修正候補（`CONFIG_CORON_DIAG_BOOT_FIX` の `lf_clean_stop`）の HFXO の待ち条件は誤り（`HFCLKSTAT.STATE==0` を待つが、HFXO を止めても HFINT に戻るだけで STATE は動作中のまま。待つべきは `SRC` が RC に戻ること）。このままでは使わない。
8. Zephyr 4.1 の起動で、`board_early_init_hook` より前に正規化されるもの（レビューの指摘。T0 でソースの行を確定する）: 外部 NVIC の有効、保留、優先度（`scb.c`、`irq_init.c`）、VTOR（`prep_c.c`）、CONTROL/MSP/PSP/BASEPRI/FAULTMASK（`reset.S`）。これらは受け渡し状態として測る意味が無く、机上で候補から外す。残るのは CLOCK、POWER、RTC1、USBD、SysTick の保留、PPI、GPIOTE。

## 無人復旧（先に確定すること。レビューで「穴の受け入れは復旧策ではない」と判定）
- 本番復帰のスクリプトは、実機が app か boot として USB に見えるときしか進めない。試験像の TIMER4 の網は入口処理と記録初期化の後に張られる。網より前で止まった場合と、優先度 0 の抑止や LOCKUP は、どの試験でも自動では戻らない。
- 方針: (1) T1 は、フックの先頭で網を張ってから写しを取る順序に変え（`net_arm()` を前へ）、網の前に増える処理を無くす。(2) T2 と T3 は、ホストから給電を切って MCU がコールドリセットすることを自動で確かめてからでないと行わない（ポートごとに給電を切れる USB ハブが要る。右手側が電池や別経路から給電されているなら VBUS を切っても落ちないので、確認で落ちなければ T2 と T3 は無人の条件では実行不可と記録する）。(3) 確認できるまで、網より前に処理を足す試験は行わない。
- 本番の更新で起動しなければ、同じ像の書き直しまでは自動で行い、それでも出ない場合は「無人の制約では戻せない」と報告して止まる。

## 手順と所要時間（レビューの見積もりに合わせた）
T0 机上（3〜5 時間、実機なし）: Zephyr の `reset.S`、`scb.c`、`irq_init.c`、`prep_c.c`、`z_arm_init_arch_hw_at_boot()`、EARLY と PRE_KERNEL_1 の初期化、nrfx の `SystemInit` が触るレジスタの表。クロックドライバ、POWER_CLOCK の共有 ISR、USB ドライバの POWER イベント登録、RTC1 のシステムタイマが前提にする入口状態から「禁止条件の表」を作る。写しの枠の形式と容量の計算。
T1 実機（試験像だけ。実装と模擬 3〜5 時間、実行約 1.5 時間、復帰 1 分）: 写しの枠、dump の行、ホストの検証表、模擬の缶詰と期待表を更新し、校正と模擬 83 場面で回帰を確かめる。ループで DFU 直後の起動（bt4 と bt4A の交互書き、稼働 1 分。1 回約 2.3 分）と `r` の起動（1 回約 1 分）を、まず各 3 回、決定的なら各 10 回、ばらつきがあれば各 20 回まで。停止条件、子の終了確認、本番復帰は既存のまま。
T3 実機（候補 B。実装 2 時間、実行 10 分。無人復旧 (2) の確認が前提）。
T2 修正（T1 で禁止条件に当たったときだけ。仕様と実装と模擬 6〜10 時間、測定 1.5 時間、本番の更新 30 分。無人復旧 (2) の確認が前提）: 整え処理か初回リセットの比較像を作り、T1 と同じ測定で「ドライバが見る入口状態が経路によらず同一で、禁止条件に当たらない」ことを確かめ、本番像に入れて通常の手順で更新し、完了条件を自動で確かめる。
USB ハブの調達は別枠。

## この方針を終えたときに言えること、言えないこと
- 言えること: DFU 直後と `r` の入口状態と、クロードライバ後、USB 有効化後の状態の経路差（項目ごと）。禁止条件に当たる項目の有無。候補 B の機構試験 1 回の結果。T2 まで進めば「ドライバが見る入口状態が経路によらず同一」という、再現に頼らない検証結果。
- 言えないこと: 現場の率は 3.40〜28.20% の幅があり、修正後の更新 N 回で 0 件でも「直った」とは言えない。修正が効いたと言えるのは、観測した禁止条件が消えた範囲まで。物理スイッチとキーマトリクスの動作は未確認のまま。
- 書き込み直後の 3 件で BLE 側も止まっていたと明記があるのは 10/05 09:26 の 1 件だけ。残り 2 件は USB の観測だけで、「本体は動いていて USB だけ出ない」は消えていない。
- 実機のブートローダーが本家 0.6.1 と同じ出口を持つかは、Seeed 配布版の差分とバイト同一性を確かめるまで推測。

## リーダーの判断が要る点
1. 無人復旧: ポートごとに給電を切れる USB ハブを入れるか（入れなければ T2 と T3 は無人の条件では行わず、T1 だけ進める）。右手側の給電経路（電池の有無）も教えてほしい。
2. 完了条件から物理キーの確認を外すこと（自動で確かめられる USB、BLE、RPC だけにする）。
3. 候補 C の「発生時に場所を残す 1 語の印」を本番に入れるか。
4. T3 の USB ETW の採取（管理者権限）を、リーダーが PC の前にいるときに承認するか。
